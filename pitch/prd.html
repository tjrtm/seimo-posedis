What we are building, and why.

Posėdis turns a single question into a full, realistic, and transparent plenary session of the Lithuanian Seimas — 141 members, real factions, voiced speeches, and a recorded vote — playable as a live broadcast and runnable entirely on local hardware. This document defines the product scope for a Python implementation.

01 Vision & problem

Public deliberation is expensive to rehearse. You cannot easily dry-run a parliamentary debate before it happens — yet communications teams, policy units, researchers and educators all need to.

Posėdis collapses that into a few minutes of compute. The user provides a topic and a language; the system convenes the full chamber and produces a structured, time-stamped session that plays back like a live broadcast — opening, ministry briefing, party-group speeches, cross-examination, debate, and a transparent recorded vote. Each of the 141 members argues in character, from their real faction and stated incentives.

The product is, at once, a deliberation sandbox, a communications rehearsal tool, a civic-education instrument, and a polished reference implementation of structured LLM output with local text-to-speech. It must run local-first: in its default configuration, no data leaves the operator's machine.

02 Target users & use cases

📣

Communications & public affairs

Pressure-test a message before a real session — see how each faction frames the issue and where the vote lands.

📊

Policy & research

Stress a proposal against 141 viewpoints; generate transcript-grade material for analysis or training data.

🎓

Civic education & journalism

Show how parliament actually works — agenda, procedure, party speeches, cross-examination, and the path to a vote.

🧪

AI & product demos

A self-contained showcase of structured generation, local TTS and real-time playback — runs with no cloud account.

Primary persona

The analyst/operator. Technically comfortable, privacy-conscious, runs the app on a workstation. Wants high-fidelity output, control over the model and voices, and the ability to archive and revisit sessions. May have an Ollama instance and a local Speaches server already; may alternatively hold an OpenAI key.

03 Goals & non-goals

Goals

  • Generate a believable, internally-consistent Seimas session from one topic, in Lithuanian or English.
  • Model all 141 members with distinct, faction-grounded behaviour.
  • Always reach a transparent recorded vote whose numbers reconcile and whose result follows the rules.
  • Play the session back as a live broadcast with per-speaker voices and an optional speaking face.
  • Run fully locally (Ollama + Speaches) or via the cloud (OpenAI), switchable at request time.
  • Persist every session as structured, re-playable data.
  • Ship as a single Python service that also serves the frontend.

Non-goals

  • Not a prediction engine — outputs are plausible simulations, never forecasts of real votes.
  • Not a real-time multi-user collaboration platform (single-operator tool in v1).
  • Not a general chatbot; the domain is fixed to Seimas plenary sessions.
  • Not a member-data authoring tool — the 141-member dataset is treated as fixed reference input.

04 Product principles

Transparency over spectacle

Every vote is auditable on screen. The viewer can always see procedure, quorum, tallies and faction breakdown.

Local-first, no lock-in

Defaults assume your own hardware. Cloud is opt-in. Secrets never leave the machine they are entered on.

Structured, not free-text

The model's output is validated against a schema. Invalid sessions are repaired or rejected — never shown raw.

Bilingual by construction

Lithuanian is the default; English is a first-class equal. Every surface exists in both.

05 Functional requirements

Requirements use MUST SHOULD COULD (MoSCoW). Each is anchored to the presentation.

5.1 — Member roster

FR-1
All 141 members MUST
The system models every member of the 2024–2028 Seimas, each with name, party/faction, a personality brief, explicit goals, abilities, constraints, and a stable assigned voice. Loaded from the preserved dataset (seimas/, seimas_members_data.js, members.json).
FR-2
Faction grounding MUST
Real factions are represented (LSDP, TS-LKD, Nemuno aušra, DSVL, Liberalai/Liberalų sąjūdis, LVŽS, LLRA-KŠS, and independents). A member's speech and vote must be consistent with their faction's stance and their own profile.
FR-3
Member directory SHOULD
Users can browse members and open a detailed profile, with search/filter by faction.

5.2 — Session generation

FR-4
Topic → session MUST
Given a free-text topic and a language, the system generates a complete session: opening & procedure, agenda, ministry briefing, party-group speeches, recess, debate & cross-examination, resolution/amendments, and a recorded vote (50–60 events total).
FR-5
Dual generation engine MUST
Two interchangeable modes selectable per request: local (transcripts via Ollama) and cloud (transcripts via OpenAI). The same request shape, schema, and validation apply to both.
FR-6
In-character speeches MUST
Each speech is 150–400 words, with concrete data, comparisons, rebuttals, and proposals, written from the speaking member's ideology.
FR-7
Validated structured output MUST
Generation returns data conforming to the session schema (see Architecture). The server validates it; on failure it repairs (one bounded retry) or surfaces a clear error — raw/invalid output is never persisted or played.

5.3 — Live broadcast playback

FR-8
Broadcast stage MUST
An LRT-style stage shows the current speaker (name, role, party), the speech text, a live updates ticker, an agenda tracker, and a progress/scrubber timeline.
FR-9
Transport controls MUST
Play/pause, restart, skip-to-next, click-to-seek, and variable speed (0.25×, 0.5×, 1×, 2×, 5×, 10×).
FR-10
Live streaming SHOULD
Events (and, when enabled, their audio) stream to the client as they become ready, so playback can begin before the whole session is synthesised.

5.4 — Voices & speaking face

FR-11
Per-speaker TTS SHOULD
When enabled, each speaker is synthesised with a stable, distinct voice and per-speaker rate. Local via Speaches (Kokoro voices, e.g. af_heart), cloud via OpenAI TTS. Output format selectable (mp3/wav/ogg).
FR-12
Animated face COULD
An optional WebGL face lip-syncs to the current audio (eye-blink, head motion), with a graceful 2D fallback when WebGL is unavailable.

5.5 — Bilingual, archive, privacy

FR-13
Bilingual generation & UI MUST
Lithuanian (default) and English. The choice drives prompts, generated content, UI strings, and the vote report, and is remembered between visits.
FR-14
Archive & replay MUST
Sessions persist as structured JSON (with any audio + a voice mapping). Saved sessions can be listed, reloaded, and replayed.
FR-15
Local-first privacy MUST
In local mode no data leaves the machine. Provider keys are supplied per request or via local environment/secret store and are never logged or persisted to session files.

5.6 The vote — transparency by law

🗳️
Per the Statute of the Seimas, deliberation concludes with a vote, and the result of a recorded vote is public. Posėdis treats this as a hard product requirement: the vote is a first-class, validated object — never prose.
FR-16
A vote is mandatory MUST
Every generated session contains at least one vote event — the final recorded vote on the resolution. Procedural votes may also appear where intermediate decisions are taken.
FR-17
Procedure & quorum MUST
Each vote states its procedure (open roll-call via the electronic system, or secret ballot) and the number of registered members. Quorum is at least 71 of 141; the report shows whether quorum was met and flags when it was not.
FR-18
Exact, reconciled tallies MUST
For / Against / Abstained (Už / Prieš / Susilaikė) counts are exact; their sum (votes cast) must not exceed 141 and must match the registered count. A per-faction breakdown is provided whose columns sum to the overall totals.
FR-19
Result by rule MUST
The result (priimta / atmesta — passed / rejected) is decided by the majority of those voting (abstentions excluded), unless a stricter threshold is declared. The system derives or verifies the result; it is never merely asserted.
FR-20
Public vote report MUST
The viewer sees a vote report (balsavimo protokolas): the question, procedure, threshold, quorum status, a colour-coded Už/Prieš/Susilaikė tally, the faction table, and any members who broke from their faction line — all on screen, in the session language.
FR-21
Self-consistency guarantee MUST
If model output is inconsistent (sums mismatch, quorum impossible, faction columns disagree), the system reconciles it deterministically before display so the published report always adds up. See Architecture › Vote model.

06 Non-functional requirements

IDCategoryRequirement
NFR-1PrivacyLocal mode performs zero outbound calls except to the operator-configured local services. No telemetry. Keys are never written to disk or logs.
NFR-2PerformanceA full session generates within a few minutes on a capable workstation; first event is playable as soon as it streams (FR-10). UI interactions stay under ~100 ms.
NFR-3ReliabilityAll model output passes schema validation; the vote always reconciles. A provider error yields a clear, actionable message, not a crash.
NFR-4PortabilitySingle Python service; runs via uvicorn locally and as a container. No build step required to serve the frontend.
NFR-5AccessibilityKeyboard-operable controls, sufficient contrast on the dark theme, captions/text always present even when audio is off.
NFR-6InternationalisationAll user-facing strings exist in LT and EN; numbers/timestamps localised; Lithuanian diacritics preserved end-to-end (UTF-8).
NFR-7Cost controlCloud usage is opt-in and surfaced; local mode incurs no per-token cost.
NFR-8MaintainabilityTyped Python (Pydantic v2), provider interfaces behind protocols, >80% test coverage on domain/validation logic.

07 Success metrics

  • Validity rate: ≥99% of generated sessions pass schema validation (after at most one repair retry).
  • Vote integrity: 100% of displayed votes are internally consistent (sums, quorum, faction reconciliation, result rule).
  • Coverage: sessions reference a realistic spread of factions and include the full structural arc.
  • Local viability: a complete session (transcript + voices) is producible with zero cloud calls.
  • Time-to-first-event: playback can start before full synthesis completes when streaming is enabled.

08 Constraints & assumptions

  • Member dataset is fixed input. The 141 profiles are reference data, preserved in the repository and loaded at startup.
  • Educational use of real names. Real member names and factions are used for civic-education purposes; the product is explicitly a simulation, labelled as such.
  • External services are operator-provided. Ollama, Speaches and OpenAI access are configured by the operator; the app does not bundle models.
  • Single operator per instance in v1; no authentication layer assumed beyond binding to localhost.

09 Out of scope (v1) & future

  • Multi-user/collaborative sessions and accounts.
  • Native Lithuanian TTS voices (pending an integrated model) — tracked as a future enhancement.
  • Executive analytics dashboards summarising many sessions.
  • Fine-tuned or custom models beyond the configured providers.
  • Mobile-native apps (the web frontend is responsive but desktop-first).
